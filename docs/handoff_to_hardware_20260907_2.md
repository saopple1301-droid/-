## 2. 【重要・要相談】現在の計測フロー設計と、その根本的な課題

### 2-1. 現状の設計

RF安全性の制約（電子レンジ動作中はセンサー基板を庫内に置けない）を踏まえ、現在のファームウェアは以下のサイクルを前提にしています。

1. 加熱前に `/start` にアクセス(風袋引き・初期画像取得)
2. 加熱(この間センサーは何もしない)
3. 一時停止・ドアを開ける
4. `/measure?heated_for_s=累積加熱秒数` にアクセスした瞬間だけセンサー読み取り(重量・表面温度・カメラ)
5. ドアを閉めて再開。中心温度推定値が閾値未満なら3〜4を繰り返す

つまり「一時停止のたびに人間がスマホでURLにアクセスする」という運用です。

### 2-2. この設計の問題点

- RF安全性は守れるが、**「開けて測って閉じる」を何度も繰り返す必要があり、実用上かなり手間**
- 一方で、完全に手入力（加熱時間だけ人間が入力）にすると、センサーとしての付加価値がほぼ消える（時間だけから中心温度が分かるなら、既存の加熱時間の目安表で十分なため）

### 2-3. 検討したい代替案：電子レンジのドアの網目窓を使う

電子レンジのドアの網目(パンチングメタル)は、可視光は通すがマイクロ波(波長 約12cm)は通さないように穴の大きさが設計されています。この性質を利用し、

- **表面温度用のMLX90640・カメラは電子レンジの外に固定し、網目窓越しに庫内を継続的に監視する**(加熱中もリアルタイムに追える可能性がある＝一時停止が不要になるかもしれない)
- **重量(ロードセル)だけは食品に接触させる必要があるため、庫内に置いたままにはできず、引き続き一時停止時にチェックする**

というハイブリッド構成にすれば、一時停止の回数を減らせる可能性があります。

### 2-4. ハードウェア側で検証・判断してほしいこと

1. 網目越しにMLX90640で温度がどこまで正確に拾えるか（金属メッシュが赤外線をどの程度遮るか、実測してみないと分からない）
2. 網目越しのカメラ画像で、庫内の食品がどこまではっきり見えるか(画角・距離・照明)
3. 外付けのカメラ/サーマルセンサー用の台をどう固定するか（レンジの機種ごとに窓の位置・サイズが違う点も考慮）
4. そもそもこの構成が現在の3Dプリント部品の設計(7章のロードセルマウント等)と両立できるか

**この案が物理的に成立しそうかどうかは、実物を触っているハードウェア側での判断が必要です。** 難しそうであれば、現状の「一時停止のたびにURLアクセス」方式のままで進めます。

## 3. 現時点でのモデル構築状況

- `measured_data_trial1.csv`にある実測データ(500W/600W、n=16)から、暫定的に以下の単回帰式を確認済み：
  `center_temp = 18.98 + 0.971 × surface_temp_mean` (R²=0.778)
- **注意**: このデータには`weight_loss_rate`(重量変化率)が含まれていません。防塵防水デジタル温度計での本番データ収集時には、重量の実測値も一緒に記録してもらえると、`train_model.py`で本来の5特徴量すべてを使ったモデルが作れます。
- `elapsed_time_s`はワット数によって同じ時間でも到達温度が変わる(500Wと600Wのデータを比較して確認済み)ため、時間そのものよりも**表面温度の方が汎用性の高い予測変数**になりそうだという見立てです。2-3の網目窓案が実現できれば、表面温度を連続的に取得できるようになるため、このモデルの精度向上にも直結します。
